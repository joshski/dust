# Audit Task Git Hook Enforcement

Extend the pre-push hook to detect and block commits from audit tasks that modify files outside `.dust/`.

## Context

Audit tasks are explicitly read-only - they should produce ideas in `.dust/ideas/` but never modify source code. Even with clear messaging in the audit templates, an eager agent might still "fix" issues it finds. A git hook provides a safety net.

### Existing Infrastructure

The pre-push hook (`lib/cli/commands/pre-push.ts`) already has infrastructure for analyzing commit changes:

- `parseGitDiffNameStatus()` parses git diff output into `FileChange[]` objects
- `analyzeChangesForTaskOnlyPattern()` checks if commits only add task files
- The hook can block pushes and emit helpful error messages
- Detection is already scoped to known agents (human pushes bypass checks)

This infrastructure could be extended to enforce that audit task commits only touch `.dust/` files.

### Detection Pattern

Audit tasks create commits with messages prefixed "Audit:" (via `transformAuditContent()` in `lib/audits/index.ts`). The hook could:

1. Detect when a commit message starts with "Audit:"
2. Check if any changed files are outside `.dust/`
3. Block push and emit helpful message if violations found

## Proposed Solution

Add a new analysis function to `pre-push.ts` that:

1. Gets the commit message for unpushed commits
2. Detects "Audit:" prefix in commit messages
3. If audit commit detected, verifies all changes are within `.dust/`
4. Blocks with instructional error message if violations found

## Related Principles

- **Stop the Line** (`stop-the-line.md`): The git hook halts and prevents defects from propagating
- **Agent Autonomy** (`agent-autonomy.md`): Enforcement enables agents to work confidently within defined boundaries
- **Actionable Errors** (`actionable-errors.md`): Error messages should tell you what to do next

## Open Questions

### How should the hook identify read-only tasks?

#### Option: Commit message prefix detection

Detect tasks by commit message prefix (e.g., commits starting with "Audit:"). This matches the current approach used by `analyzeChangesForTaskOnlyPattern()`.

Pros: Simple, works with current commit conventions, no changes to task file format
Cons: Relies on commit message discipline, any task with "Audit:" prefix gets enforced

#### Option: Task file metadata

Add a `## Generated By` or `## Read-Only: true` section to audit task files. The hook reads the task file being completed and checks for this metadata.

Pros: Self-documenting tasks, metadata lives with the task, could extend to other read-only task types
Cons: Requires parsing task files during pre-push, more implementation complexity

### Should the enforcement be enabled by default?

#### Option: Enabled by default

The hook always checks audit commits for non-`.dust/` changes.

Pros: Immediate protection, opt-out rather than opt-in, consistent behavior
Cons: May surprise users if they intentionally want audits to make changes

#### Option: Opt-in via configuration

Add a setting like `"enforceAuditScope": true` to `.dust/config/settings.json`.

Pros: Non-breaking, allows gradual adoption
Cons: Many repositories won't enable it, reduces protection

#### Option: Enabled only in unattended mode

Check is active when `DUST_UNATTENDED=1` but not during interactive sessions.

Pros: Protects autonomous agents while allowing human flexibility
Cons: Inconsistent behavior between modes, most agent sessions aren't unattended

### What error message format should the hook use?

#### Option: Terse technical message

```
Push blocked: Audit task modified files outside .dust/
  -> src/parser.ts
  -> lib/utils.ts
```

Pros: Concise, clear for experienced users
Cons: May not guide agents effectively

#### Option: Instructional message with guidance

```
Push blocked: Audit tasks should not modify source code.

This commit is prefixed with "Audit:" but includes changes to:
  -> src/parser.ts
  -> lib/utils.ts

Audit tasks should only create or modify files in .dust/ideas/.
If these changes are intentional, create a separate task to implement them.
```

Pros: Clearer guidance for agents, explains the constraint
Cons: More verbose output
